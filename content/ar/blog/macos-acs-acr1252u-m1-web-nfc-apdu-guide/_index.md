> **المنتج المقدَّم**: ACS ACR1252U-M1 (USB NFC Reader III، قارئ بطاقات معتمد من NFC Forum)
> **الفئة المستهدفة**: مطوّرو تطبيقات macOS (Apple Silicon)، ومهندسو الواجهات الأمامية لـ Web NFC، ومختبرو البطاقات الذكية وأنظمة التحكم بالدخول، وصنّاع المشاريع (Maker) وباحثو المختبرات
> **هدف المقال**: فهم معايير CCID / PC/SC الكامنة خلف «الدعم الأصلي في macOS» دفعة واحدة، ومعرفة كيفية التعامل مع علامات NTAG213/NTAG215 عبر مساري التطوير — Web NFC في المتصفح وAPDU في البرامج المحلية — بما في ذلك التحكم بالبايتات في جرس القارئ وLED ثنائي اللون.

---

> **⚠️ حدود الدعم الأهم أولاً (اقرأ قبل الطلب)**
> 1. **يدعم Web NFC API حالياً متصفحات Chromium فقط، وعلى أجهزة Android وChromeOS حصراً**. متصفح Chrome لسطح المكتب على macOS／Windows／Linux، وEdge لسطح المكتب، وFirefox، وSafari — جميعها **لا تملك** واجهة `NDEFReader`.
> 2. **Safari على macOS وiOS (أي متصفح) لا يدعمان Web NFC إطلاقاً**؛ للاستفادة من NFC على iOS لا بد من إطار Core NFC الأصلي (يتطلب كتابة تطبيق).
> 3. **يستخدم Web NFC في المتصفح «وحدة NFC المدمجة في الجهاز»** (مثل هاتف Android أو حاسوب ChromeOS المحمول)، **وليس** قارئ USB خارجياً. أما ACR1252U-M1 الخارجي فيعمل وفق معيار PC/SC ويُتحكم فيه عبر أوامر APDU من البرامج المحلية — المساران منفصلان، لذا تأكد من منصتك المستهدفة قبل الشراء.

## البداية: بطاقة NFC واحدة، مساران للتطوير

لنفترض أن لديك علامة NTAG215 للتحكم بالدخول أو لمكافحة التزييف، وتريد تحويلها إلى بيانات يمكن قراءتها وكتابتها داخل «المتصفح». وفي الوقت نفسه، تريد كتابة برنامج أدوات على macOS يتحكم بالقارئ بالبايتات لـ«إصدار صوت تنبيه واحد وإضاءة خضراء».

هذان المطلبان يقابلان تقنيتين مختلفتين تماماً:

1. **Web NFC API**: داخل المتصفحات المدعومة (Chromium على Android／ChromeOS)، يمكنك قراءة وكتابة علامات NDEF مباشرة ببضعة أسطر من JavaScript، دون الحاجة إلى أي عتاد قارئ.
2. **APDU (Application Protocol Data Unit)**: عبر معيار PC/SC، ترسل البرامج المحلية (Swift، Python…) أوامر بايتية إلى القارئ، ويمتد نطاق التحكم إلى «الجهاز نفسه خارج البطاقة» — مثل جرس القارئ وLED ثنائي اللون.

أما **ACS ACR1252U-M1** فهو مناسب ليكون قارئك الأول للتطوير لأنه يتوافق مع معيار **CCID** وحاصل على اعتماد **PC/SC** و**NFC Forum**، ويعمل على macOS **بمجرد التوصيل دون تثبيت أي برنامج تشغيل خارجي**. فيما يلي ثلاثة أقسام: «لماذا يهم الدعم الأصلي»، و«كيف تطبّق Web NFC عملياً»، و«كيف تتحكم بالضوء والجرس عبر APDU»، مع ورقة عمل تأكيد ما قبل الشراء في النهاية.

## أولاً: CCID وPC/SC على أجهزة Apple Silicon Mac: لماذا يهم «الدعم الأصلي» للمطوّرين

### 1.1 توضيح ثلاثة مصطلحات: CCID وPC/SC والدعم الأصلي

| المصطلح | الاسم الكامل | شرح في جملة واحدة |
|---|---|---|
| CCID | Chip Card Interface Device | **فئة USB قياسية (USB Class)** تحدد كيفية تواصل قارئ البطاقات الذكية عبر USB. في الأجهزة المتوافقة مع CCID، يتولى نظام التشغيل معالجة بروتوكول الاتصال. |
| PC/SC | Personal Computer/Smart Card | **معيار API** يتيح للتطبيقات الوصول إلى قارئ البطاقات الذكية عبر واجهة موحدة، دون الاهتمام بالرقاقة المستخدمة في الطبقة السفلية. |
| الدعم الأصلي | Driverless / Built-in Driver | نظام التشغيل **يضم مدمجاً** برنامج تشغيل لهذه الفئة؛ توصّل الجهاز فيعمل فوراً، دون «تثبيت قرص برنامج تشغيل من الشركة المصنعة». |

بكلمات بسيطة: يضع CCID قاعدة موحدة لـ«كيف يتحدث القارئ مع الحاسوب» كمواصفة USB، ويضع PC/SC واجهة API موحدة لـ«كيف تستدعي التطبيقات القارئ». وعند توفر الاثنين معاً، يستطيع نظام التشغيل دعم الجهاز مباشرة على مستوى النواة، وهذا هو «الدعم الأصلي».

حصل ACR1252U-M1 على اعتمادات متعددة تشمل **CCID وPC/SC وNFC Forum وFeliCa Performance** (كما هو موثق في ورقة المواصفات). وهذا يعني أنه يعمل بالتوصيل والتشغيل على **أي** نظام تشغيل يطبّق هذين المعيارين.

### 1.2 لماذا يهم هذا الأمر بشكل خاص على Apple Silicon

في عصر Apple Silicon (M1／M2／M3／M4)، شدّد macOS القيود على برامج التشغيل الخارجية بشكل كبير:

- **تُعامل امتدادات النواة (Kernel Extension / kext) كتقنية انتقالية**: تحديثات النظام وأمان قرص الإقلاع (Secure Boot) تحجب بقوة برامج التشغيل غير الموقّعة وغير الموثّقة. الحفاظ على برنامج تشغيل macOS يمكن للمستخدمين «تثبيته فعلياً» مكلف جداً للشركات المصنعة، وكثير من المنتجات تتخلى عن ذلك.
- **يضم macOS إطار Smart Card Services مدمجاً**، ويتضمن دعماً لقارئات CCID. لذلك لا يحتاج القارئ المتوافق مع CCID **إلى أي برنامج تشغيل من الشركة المصنعة على macOS** — نظام التشغيل يتعرف عليه بنفسه.

هذه هي القيمة الحقيقية لـ«الدعم الأصلي»: لا تنتظر إصدار برنامج تشغيل جديد متوافق مع سلسلة M من الشركة المصنعة، ولا تقلق بشأن Team ID أو التوثيق (Notarization). **تحديثات macOS الرئيسية لا تؤثر على عمل القارئ أيضاً**.

التحقق من أن النظام تعرف على القارئ (على macOS):

```bash
# عرض قارئات البطاقات الذكية (ظهور ACR1252U / ACS يعني أن النظام عدّد الجهاز)
system_profiler SPCardReaderDataType

# بعد تثبيت pcsc-tools (حزمة brew) يمكن استخدام pcsc_scan للمراقبة اللحظية
brew install pcsc-tools
pcsc_scan
```

### 1.3 الأهمية العملية للمطوّرين

| سيناريو التطوير | قارئ غير CCID | ACR1252U-M1 (CCID／PC/SC) |
|---|---|---|
| تثبيت برنامج التشغيل على macOS | ملف تثبيت من الشركة + توقيع وتوثيق | **بدون تثبيت، توصيل وتشغيل** |
| بعد تحديث macOS الرئيسي | غالباً يتعطل (انتهاء التوقيع أو رفض kext) | لا يتأثر |
| تغيير حاسوب التطوير | إعادة تثبيت برنامج التشغيل على كل جهاز | توصيل مباشر |
| عبر المنصات (macOS／Linux／Windows) | برامج تشغيل غير متسقة بين الشركات | نفس أوامر PC/SC |
| حماية أمان macOS | بعضها يتطلب خفض إعدادات الأمان للتحميل | **لا حاجة لتعطيل أي حماية أمان إطلاقاً** |

> **خط أحمر أمني**: يعمل هذا المنتج وجميع خطوات هذا المقال ضمن إعدادات أمان macOS الافتراضية (الأمان الكامل، حماية تكامل النظام SIP مفعّلة). إذا واجهت تعذر تحميل برنامج تشغيل على منصة أخرى، **لا تتجاوز ذلك بتعطيل Secure Boot أو خفض مستوى الأمان** — الطريقة الصحيحة هي استخدام جهاز متوافق مع معيار CCID، أو اتباع إجراء التوقيع المدعوم من نظام التشغيل.

## ثانياً: تطبيق Web NFC API عملياً: قراءة وكتابة NTAG213 / NTAG215 في المتصفح

### 2.1 تأكد أولاً من نطاق الدعم (نقطة Support Reduction الأساسية)

واجهات Web NFC API (مثل `NDEFReader`／`NDEFWriter`) **ليست متوفرة في كل المتصفحات**. الجدول التالي يوضح الوضع الفعلي في عام 2026:

| البيئة | المتصفح | Web NFC (NDEFReader) | ملاحظات |
|---|---|---|---|
| Android | Chrome／Edge／Samsung Internet (قائمة على Chromium) | ✅ مدعوم | يتطلب HTTPS أو localhost، بالإضافة إلى إيماءة من المستخدم |
| ChromeOS | Chrome المدمج في ChromeOS | ✅ مدعوم | يتطلب أن يمتلك الجهاز وحدة تحكم NFC |
| macOS سطح المكتب | Chrome／Edge لسطح المكتب | ❌ غير مدعوم | **Chrome لسطح المكتب لا يملك Web NFC** |
| macOS سطح المكتب | Safari | ❌ غير مدعوم | غير متوفر في جميع إصدارات Safari |
| Windows／Linux سطح المكتب | Chrome／Edge／Firefox لسطح المكتب | ❌ غير مدعوم | Web NFC غير متاح لإصدارات سطح المكتب |
| iOS (iPhone／iPad) | أي متصفح (بما في ذلك Chrome وEdge iOS) | ❌ غير مدعوم | جميع متصفحات iOS تستخدم WebKit؛ للاستفادة من NFC لا بد من Core NFC في تطبيق أصلي |

**الخلاصة**: للعمل الفعلي على علامات NFC داخل «المتصفح»، تحتاج إلى **هاتف Android أو جهاز ChromeOS**. أما على سطح مكتب macOS، فقيمة ACR1252U-M1 تكمن في **تطوير البرامج المحلية عبر PC/SC** المذكور في الفصلين الثاني والثالث — قراءة وكتابة نفس العلامات، أو إرسال أوامر APDU للتحكم بالقارئ.

> **مفهوم خاطئ رئيسي آخر**: يستخدم Web NFC داخل المتصفح **رقاقة NFC المدمجة في الجهاز** (وحدة تحكم NFC في الهاتف أو حاسوب ChromeOS المحمول)، **ولن يستخدم المتصفح قارئ USB خارجياً أبداً**. لذا ليس صحيحاً أن «توصيل ACR1252U-M1 بحاسوب Chromebook يجعل صفحة الويب تقرأ البطاقات». مصدر العتاد في المسارين مختلف.

### 2.2 العلامات المطلوبة: NTAG213 وNTAG215

صيغة NDEF التي يعتمدها Web NFC ترتبط غالباً بعلامات **NFC Forum Type 2**، أي سلسلة NXP **NTAG213 / NTAG215 / NTAG216** (شائعة في التحكم بالدخول، وبطاقات الأعمال، ومكافحة التزييف، وبدائل Amiibo وغيرها):

| البند | NTAG213 | NTAG215 |
|---|---|---|
| ذاكرة المستخدم | 144 bytes | 504 bytes |
| السعة المتاحة لـ NDEF | نحو 137 bytes | نحو 496 bytes |
| الاستخدام النموذجي | روابط قصيرة، بطاقة أعمال واحدة، بيانات صغيرة | بيانات متوسطة (JSON أطول／سجلات متعددة) |
| سرعة القراءة/الكتابة | 106 kbps (يحددها القارئ فعلياً) | 106 kbps |
| الأمان | حماية بكلمة مرور واحدة | حماية بكلمة مرور واحدة |

> مفهوم السعة: 137 bytes تكفي لنحو 130 حرفاً إنجليزياً؛ للمحتوى المتوسط أقل من 1KB، أو لتجربة «سجلات متعددة في بطاقة واحدة»، اختر NTAG215. في بداية التطوير يُنصح **بتجهيز مجموعة من العلامات الفارغة** (فارغة، غير مقفلة، بدون كلمة مرور) لتسهيل إعادة الكتابة المتكررة.
>
> أما عن «القفل» فهناك حالتان: بعد **تعيين كلمة مرور**، لا يزال بإمكانك التحقق منها عبر أمر PWD_AUTH ومواصلة الكتابة؛ ما لا رجعة فيه حقاً هو **كتابة بتات القفل (Lock Bits)** — بمجرد القفل، لا تعود صلاحية الكتابة أبداً.

### 2.3 مثال القراءة (NDEFReader.scan)

افتح أولاً صفحة **HTTPS (أو localhost)** على Android Chrome／ChromeOS Chrome، وضع العلامة على منطقة هوائي NFC في الجهاز. مثال:

```html
<!DOCTYPE html>
<html lang="zh-Hant">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Web NFC 讀寫示範</title>
</head>
<body>
  <h1>Web NFC 讀寫示範</h1>
  <button id="btnScan">開始掃描</button>
  <button id="btnWrite">寫入標籤</button>
  <pre id="output"></pre>

  <script>
    const out = (msg) => {
      document.getElementById('output').textContent += msg + '\n';
    };

    if (!('NDEFReader' in window)) {
      out('此瀏覽器不支援 Web NFC（NDEFReader）。\n請改用 Android Chrome 或 ChromeOS Chrome。');
    }

    // 讀取：scan() 需使用者手勢觸發
    document.getElementById('btnScan').addEventListener('click', async () => {
      try {
        const reader = new NDEFReader();
        await reader.scan();
        out('已開始掃描，請將標籤靠近手機 NFC 感應區…');

        reader.onreading = (event) => {
          out('--- 讀取到標籤 ---');
          out('序列號（Serial Number）：' + event.serialNumber);
          for (const record of event.message.records) {
            out('recordType：' + record.recordType);
            if (record.recordType === 'text' || record.recordType === 'url') {
              out('內容：' + record.data);
            } else {
              out('內容（二進位 ByteArray）：' + new Uint8Array(record.data));
            }
          }
        };

        reader.onreadingerror = () => out('讀取錯誤：請確認標籤是否支援 NDEF。');
      } catch (err) {
        out('scan() 失敗：' + err.name + ' / ' + err.message);
      }
    });
  </script>
</body>
</html>
```

> بالنسبة لعلامات NTAG213／NTAG215 (Type 2)، يقسّم `event.message` رسالة NDEF الموجودة على العلامة إلى `records`: بالنسبة لنوعي `text` و`url` يكون `record.data` نصاً جاهزاً مباشرة؛ أما الأنواع الأخرى فتكون `ArrayBuffer` وتحتاج إلى تحويل يدوي.

### 2.4 مثال الكتابة (NDEFReader.write)

غيّر معالج زر الصفحة أعلاه إلى:

```javascript
// 寫入：write() 同樣需使用者手勢，且標籤需在感應範圍內
document.getElementById('btnWrite').addEventListener('click', async () => {
  try {
    const writer = new NDEFReader();

    // 方式一：直接寫一段文字（自動包成 text 記錄）
    // await writer.write('Yupitek Web NFC 測試');

    // 方式二：寫入一筆網址記錄（適合名片、導流）
    await writer.write({
      records: [
        { type: 'url', data: 'https://www.yupitek.com' },
        { type: 'text', data: 'ALFA / ACS 產品技術部落格' },
      ],
    });

    out('寫入成功！');
  } catch (err) {
    out('寫入失敗：' + err.name + ' / ' + err.message);
  }
});
```

بعد اكتمال الكتابة، ضع نفس العلامة على ACR1252U-M1 (أو أي أداة قراءة تدعم NDEF) للتأكد من أن المحتوى كُتب بشكل صحيح.

### 2.5 المزالق الشائعة (تلميحات Debugging)

| العَرَض | السبب | طريقة المعالجة |
|---|---|---|
| تظهر الصفحة «NDEFReader is not defined» | Chrome／Safari／Firefox لسطح المكتب لا تدعم Web NFC | استخدم Android Chrome أو ChromeOS؛ وعلى macOS اتبع مسار PC/SC |
| يرمي `scan()` خطأ NotAllowedError | غياب إيماءة المستخدم، أو عدم التواجد على صفحة HTTPS | استدعِه بعد النقر على الزر؛ وللتطوير المحلي استخدم `http://localhost` |
| استشعار العلامة مع استمرار onreadingerror | سعة العلامة غير كافية، تلف التنسيق، أو البطاقة لا تدعم NDEF | جرّب علامة NTAG213/215 فارغة غير مقفلة |
| فشل الكتابة في منتصفها | العلامة مقفلة (Lock Bits) أو تجاوزت السعة | تحقق من السعة (137／496 bytes) وبتات القفل؛ العلامات المقفلة لا يمكن استعادتها |
| لا تصل أحداث بعد مغادرة التبويب／إطفاء الشاشة | يعمل Web NFC فقط عندما يكون التبويب **في المقدمة ومركّزاً** | أبقِ التبويب مفتوحاً؛ المسح في الخلفية ليس من تصميم Web NFC |

> **تنبيه أمني (ما لا يجب فعله)**: يستطيع Web NFC قراءة وكتابة «ما تسمح به العلامة لك» فقط. إذا كانت البطاقة تطبّق التحقق بكلمة مرور، أو قناة آمنة ISO 14443-4، أو تشفيراً (مثل التحقق الخلفي في أنظمة التحكم بالدخول)، **فلا يستطيع المتصفح — ولا ينبغي له — تجاوز آلية الأمان الخاصة بها**. جميع الدروس في هذا المقال مقصورة على علامات فارغة وبطاقات اختبار تملكها أو مُخوَّل باستخدامها.

## ثالثاً: تطوير أوامر APDU: التحكم بالجرس وLED ثنائي اللون عبر البايتات

APDU هي «اللغة منخفضة المستوى» في عالم البطاقات الذكية والقارئات. لقد غلّف لك Web NFC تنسيق البيانات؛ أما **قيادة قارئ ACR1252U-M1 نفسه على macOS — التحكم بالأضواء والجرس — فتتطلب إرسال APDU مباشرة**.

### 3.1 البنية الأساسية لـ APDU

الأمر المرسل إلى القارئ／البطاقة هو سلسلة بايتات بالصيغة التالية:

```
CLA  INS  P1  P2  Lc   Data(0~N bytes)   Le
└─فئة الأمر┘└─الأمر┘└─المعلمات┘  └─طول البيانات┘  └─طول الاستجابة المتوقعة┘
```

- **CLA**: فئة الأمر (0x00 = معيار ISO 7816؛ 0xFF = مساحة أوامر الشركة المصنعة).
- **INS**: رمز الأمر (0xA4 = SELECT، 0x20 = VERIFY، 0xCA = GET DATA…).
- **P1 P2**: بايتا معلمات.
- **Lc**: طول Data التالية (يمكن حذفه).
- **Le**: طول الاستجابة (Response) المتوقعة (يمكن حذفه).

أما الاستجابة فهي بيانات تليها بايتا ختام **SW1 SW2**؛ من الشائع `90 00` (نجاح)، و`6A 82` (ملف غير موجود)، و`63 00` (فشل التحقق).

### 3.2 تجهيز بيئة التطوير على macOS

يضم macOS دعماً مدمجاً لـ PC/SC، لذا يكفي تثبيت `pyscard` الخاص بـ Python لإرسال APDU مباشرة:

```bash
# تثبيت pcsc-tools (يتضمن pcsc_scan، مفيد للتأكد من القارئ)
brew install pcsc-tools

# تثبيت pyscard (عبر إطار PC/SC الخاص بنظام macOS)
pip install pyscard

# التأكد من أن pyscard يستطيع سرد القارئات
python3 -c "from smartcard.System import readers; print(readers())"
# الإخراج المتوقع تقريباً: ['ACS ACR1252U ... 00 00']
```

### 3.3 أول APDU: Echo وإصدار البرنامج الثابت

يدعم ACR1252U-M1 «أمر Echo» القياسي من ACS، ويمكن استخدامه كاختبار اتصال؛ ثم اقرأ إصدار البرنامج الثابت للتأكد من سلامة التواصل مع الحاسوب:

```python
from smartcard.System import readers
from smartcard.util import toHexString

reader = readers()[0]
conn = reader.createConnection()
conn.connect()

# 1) Echo: يعيد ASCII "12345678"
sw, data = conn.transmit([0xFF, 0x00, 0x00, 0x00, 0x00])
print('Echo SW :', toHexString(sw))
print('Echo 回傳:', ''.join(chr(b) for b in data))

# 2) إصدار البرنامج الثابت
sw, data = conn.transmit([0xFF, 0x00, 0x48, 0x00, 0x00])
print('Firmware:', toHexString(data))
```

ظهور `12345678` يعني أن قناة PC/SC سليمة وأن برنامج القارئ الثابت يستجيب بشكل طبيعي.

### 3.4 إرسال APDU إلى بطاقة: مثال MIFARE DESFire

تخيّل البطاقة اللاتلامسية كـ«نظام بريدي للبايتات»: ترسل أمراً، فتعيد إليك بيانات. باستخدام بطاقة اختبار **MIFARE DESFire** التي تدعم APDU الحقيقي (ISO 14443-4)، أرسل أمر «Get Version» (`90 60 00 00 00`):

```python
# DESFire GetVersion: البايت الأول 0x04 في الاستجابة يعني سلسلة DESFire (EV1/EV2/EV3)
sw, data = conn.transmit([0x90, 0x60, 0x00, 0x00, 0x00])
print('SW  :', toHexString(sw))
print('Data:', toHexString(data))
# مثال: 04 01 01 00 04 12 08 01
#       └DESFire┘└سلسلة الإصدار┘     └البرنامج الثابت/العتاد/رقم الدفعة…┘
```

> إذا لم تتوفر لديك بطاقة DESFire، يمكنك استخدام **أمر PPSE** للاستكشاف السلبي لأي بطاقة دفع لاتلامسية EMV: `00 A4 04 00 0E 32 50 41 59 2E 53 59 53 2E 44 44 46 30 31 00` (SELECT "2PAY.SYS.DDF01"). على بطاقات الاختبار الخاصة بك فقط.

### 3.5 التحكم بالجرس وLED ثنائي اللون (أحمر／أخضر)

يضم جسم ACR1252U-M1 **LED ثنائي اللون (أحمر／أخضر)** و**جرساً أحادي النغمة**، وكلاهما «قابل للتحكم من المستخدم». وهذا هو أكثر أشكال التغذية الراجعة شيوعاً في التطبيقات: نجاح التحقق من البطاقة → تنبيه واحد + ضوء أخضر؛ فشل التحقق → وميض أحمر. تعرف النتيجة دون النظر إلى الشاشة.

للتحكم في وظائف «جسم القارئ» هذه، يُستخدم **مساحة أوامر الشركة المصنعة** (أوامر APDU التي تبدأ بادئتها بـ `FF`؛ `CLA=0xFF` هي المنطقة المحجوزة لأوامر الشركة). البنية النموذجية كما يلي (**مطابقة البايتات تختلف حسب إصدار البرنامج الثابت؛ قبل التطوير اعتمد على وثيقة ACS الرسمية «ACR1252U-M1 Application Programming Interface»**):

```
FF  00  40  00  04  00  00  <LED>  <BUZZER>
└─بادئة أمر الشركة─┘   └Len┘ └─المعلمات─┘  └الضوء┘ └مدة التنبيه┘
```

| المعلمة | قيمة مثال | المعنى (وفق البرنامج الثابت المثال) |
|---|---|---|
| LED | 0x00 | إطفاء |
| LED | 0x01 | إضاءة حمراء |
| LED | 0x02 | إضاءة خضراء |
| LED | 0x03 | أحمر＋أخضر معاً |
| BUZZER | 0x00 | بدون تنبيه |
| BUZZER | 0x04 | تنبيه نحو ثانية واحدة (وحدة الوقت وفق الوثيقة الرسمية)|

```python
# إضاءة خضراء + تنبيه قصير (بايتات مثال؛ راجع وثيقة API الرسمية لإصدار برنامجك الثابت)
sw, data = conn.transmit([0xFF, 0x00, 0x40, 0x00, 0x04, 0x00, 0x00, 0x02, 0x04])
print('LED/Buzzer 回應:', toHexString(sw))   # متوقع 90 00 (نجاح)

# إطفاء
sw, data = conn.transmit([0xFF, 0x00, 0x40, 0x00, 0x04, 0x00, 0x00, 0x00, 0x00])
```

> **تنبيه تطويري**: قد تختلف تعريفات البايتات ووحدات الوقت بين إصدارات البرنامج الثابت. الطريقة الصحيحة: اقرأ أولاً إصدار البرنامج الثابت بأمر `3.3`، ثم راجع وثيقة API الرسمية لذلك الإصدار لتأكيد تعريف بايتات `LED`／`BUZZER`، وتحقق عملياً من `SW1 SW2 = 90 00`. الغرض من أمثلة هذا المقال هو عرض منهجية «التحكم بجسم الجهاز عبر البايتات»، وليس تجاوز آلية تحقق أي بطاقة.
>
> **خط أحمر أمني**: التحكم بالجرس وأضواء LED هو **سلوك مرئي لجسم القارئ**، ولا علاقة له بـ«إمكانية نسخ محتوى البطاقة أو تزييفه». لا يقدم هذا المقال **ولا يتناول** أي طريقة لنسخ بطاقات الدخول اللاتلامسية، أو تجاوز كلمات مرور البطاقات أو تحققها الأمني؛ جميع اختبارات APDU مقصورة على بطاقات وأجهزة تملكها أو مُخوَّل باستخدامها صراحة.

## خامساً: الخاتمة

بالنسبة للمطوّرين على Apple Silicon، «الدعم الأصلي» ليس صفة، بل **حقيقة هندسية قابلة للتحقق**. عبر معياري CCID / PC/SC، يتيح ACR1252U-M1 بدء التطوير على macOS دون تثبيت أي برنامج تشغيل. وبالاقتران مع Web NFC (Chromium／Android／ChromeOS) وPC/SC APDU (محلي على macOS)، يمكن لنفس دفعة علامات NTAG213／NTAG215 أن تتيح تمريناً كاملاً على «القراءة والكتابة والتحكم» عبر المسارين التقنيين.

تذكر أمرين: **تأكد أولاً من نطاق دعم متصفحك** (Web NFC مقصور على Chromium على Android／ChromeOS)، **ثم حدد ما إذا كنت بحاجة للتحكم بجسم القارئ** (وهذا عمل APDU). أما الباقي فاتركه للبايتات.
