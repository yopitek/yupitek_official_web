## 서두: "시스템 업데이트할 때마다 드라이버 재컴파일"하던 그 나날들

Realtek RTL8812AU 계열 칩셋(인기 있는 AWUS036ACH 등)을 기반으로 한 USB 어댑터를 써본 적이 있다면, 아마 이런 일을 겪어봤을 것입니다.

1. 커뮤니티가 관리하는 드라이버를 설치하면 인터넷과 모니터링이 잘 작동합니다.
2. 어느 날 `sudo apt upgrade`를 실행하면 Linux 커널이 새 버전으로 바뀝니다.
3. 재부팅 후 어댑터가 시스템에서 사라집니다 — Wi-Fi 인터페이스(`wlan0` / `wlan1`)가 어디에도 없습니다.
4. 결국 **소스를 다시 다운로드하고, DKMS를 설치하고, 커널 모듈을 재컴파일**하며 — 오후 한나절을 통째로 날립니다.

문제는 하드웨어가 아닙니다. 드라이버가 취하는 형태가 문제입니다. 대부분의 Realtek Linux 드라이버는 Linux 커널(메인라인)에 병합되어 있지 않습니다. 이를 사용하려면 외부 소스 코드를 시스템에 덧붙여야 합니다. 커널이 업그레이드될 때마다 그 덧붙인 부분을 재컴파일해야 하고 — 그렇지 않으면 새 커널과 맞지 않아 작동을 멈춥니다.

오늘의 주인공 — MediaTek MT7921AUN를 탑재한 ALFA AWUS036AXML — 은 완전히 다른 길을 택합니다. 그 드라이버는 **Linux 커널 안에 네이티브로 자리 잡고 있습니다**.

## 1. Linux 커널이 업데이트될 때 Realtek 드라이버 빌드가 깨지는 이유

### 1.1 커널 모듈은 특정 커널 버전에 묶여 있다

Linux 커널은 디바이스 드라이버를 "모듈"로 동적으로 로드합니다. 핵심은 이것입니다. **모듈은 특정 커널 버전에 맞춰 컴파일됩니다.** 주요 커널 업데이트(예: 6.8 → 6.9) 이후에는 기존 모듈이 대개 새 커널에서 로드되지 못하며 — 반드시 재컴파일해야 합니다.

### 1.2 DKMS: 새로운 함정을 동반한 자동 재컴파일 생명줄

DKMS(Dynamic Kernel Module Support)는 바로 이 "커널이 업데이트되면 모듈을 다시 빌드해야 하는" 고통을 해결하기 위해 존재합니다. 커널이 업그레이드될 때마다 **드라이버를 자동으로 재컴파일해 줍니다.** 좋게 들리지만 실제로는 여전히 다음과 같은 문제를 만납니다.

- **툴체인 문제**: 빌드에는 `build-essential`, `dkms`, 그리고 네이티브 커널 헤더(`linux-headers-$(uname -r)`)가 필요합니다. 하나라도 빠지면 DKMS 빌드가 즉시 실패합니다.
- **버전 비호환성**: 최악의 경우는 GitHub 드라이버가 새 API 변경을 따라잡기 전에 커널 업그레이드가 먼저 이루어지는 상황입니다. 다음 `apt upgrade`가 바로 망가지는 업그레이드일지 결코 알 수 없습니다.
- **Secure Boot / 커널 모듈 서명**: Secure Boot가 활성화되어 있으면 시스템이 서명되지 않은 커널 모듈을 거부합니다 — 어댑터 인터페이스가 아예 나타나지 않습니다. 보안을 끄는 방식으로는 해결할 수 없으며, 올바른 방법은 MOK(Machine Owner Key) 메커니즘을 통해 자체 서명 인증서를 가져오는 것입니다. 또 하나의 번거로운 일거리입니다.
- **커뮤니티 포크 불안**: 같은 칩셋에 `aircrack-ng/rtl8812au`, `morrownr/8812au-20210820` 등 여러 GitHub 브랜치가 있으며, 버전과 지원 커널 범위가 제각각입니다. 잘못 고르면 빌드 전체가 헛수고가 됩니다.

### 1.3 당신의 시간이 진짜 비용이다

설치 시 한 번만 컴파일하면 된다면 괜찮습니다. 하지만 **시스템이 계속 업데이트되는 한, 그 드라이버는 영구적인 유지보수 부담입니다.** 침투 테스터와 임베디드 개발자에게 소중한 시간은 도구와 스크립트에 투입되어야지 — Wi-Fi 어댑터 드라이버 재컴파일에 쓰여서는 안 됩니다.

## 2. MediaTek MT7921AU: "네이티브 지원, 플러그 앤 플레이"가 작동하는 이유

### 2.1 네이티브 지원이 이루어지는 방식: mt76와 mt7921u

MediaTek의 Wi-Fi 칩셋 드라이버는 오랫동안 Linux 커널의 mt76 무선 드라이버 프레임워크 안에 자리해 왔습니다. MT7921 제품군에는 PCIe와 USB 변형이 있습니다.

- MT7921 제품군은 Linux 커널 5.12(PCIe / M.2 버전)에서 처음 메인라인에 진입했으며,
- AWUS036AXML은 USB용 `mt7921u` 드라이버를 사용하는데, 이는 Linux 커널 5.18부터 메인라인에 네이티브로 포함되어 있습니다.

다시 말해 **GitHub에서 가져올 소스 코드도, DKMS도, 자체 컴파일도 없습니다.** 배포판 커널이 충분히 새롭기만 하면, 어댑터를 꽂고 펌웨어 파일을 추가하면 끝입니다. 인터페이스가 `ip link`에 나타납니다.

### 2.2 드라이버 소스 코드가 아니라 펌웨어만 필요하다

많은 사람이 "컴파일 불필요"를 "설치할 것이 전혀 없음"으로 오해합니다. 정확하지 않습니다. "드라이버 컴파일 불필요"가 "아예 설치가 없음"을 뜻하지는 않습니다. MT7921AU는 드라이버 소스 코드가 아니라 **펌웨어 파일**이 필요합니다. 펌웨어는 배포판 패키지로 관리되며, 보통 단일 명령으로 해결됩니다.

```bash
sudo apt update
sudo apt install linux-firmware firmware-misc-nonfree   # Debian / Kali 계열
sudo reboot
```

Ubuntu의 일반적인 방식:

```bash
sudo apt update
sudo apt install linux-firmware
sudo reboot
```

펌웨어는 "배포판을 따라가는" 패키지입니다 — 커널 업그레이드가 이를 깨뜨릴 수 없습니다. 이것이 DKMS 드라이버와의 근본적인 유지보수 차이입니다.

배포판별 최소 커널 요구 사항을 한눈에 정리하면:

| OS / 배포판 | 최소 커널 | 드라이버 컴파일 필요? |
|---|---|---|
| Kali Linux (Rolling) | 6.x (`mt7921u` 포함) | 아니오, 펌웨어만 추가 |
| Debian 12 | 6.1 LTS | 아니오 |
| Ubuntu 22.04+ / 24.04 LTS | 5.18+ (HWE 커널 권장) | 아니오 |
| Raspberry Pi OS (Bookworm) | 6.1 LTS | 아니오 |
| 구형 Linux 배포판 | 5.18 미만 | 추가 작업 필요; 권장하지 않음 |
| Windows 10 / 11 | — | 벤더 드라이버 |
| macOS (Intel / Apple Silicon) | 지원 안 됨 | **드라이버 없음 — 구매하지 마십시오** |

> **⚠️ 구매 전 가장 중요한 지원 참고 사항**: AWUS036AXML은 **macOS를 지원하지 않습니다.** 오늘날 Intel도 Apple Silicon도 사용 가능한 MT7921AUN macOS 드라이버가 없습니다. macOS가 주 환경이라면 이 부류의 Wi-Fi 6 / 6E USB 어댑터는 막다른 길입니다 — 구매 후에 알게 되기 전에, 지금 배제하십시오.

### 2.3 네이티브 지원이 Kali 개발자에게 특히 중요한 이유

Kali Linux에서는 커널 업그레이드가 매우 빈번합니다(Rolling 릴리스이기 때문). RTL8812AU 사용자는 롤링 업데이트마다 숨을 죽입니다. 반면 `mt7921u`는 커널과 함께 관리·테스트되므로 — **커널이 아무리 새로워져도 드라이버가 따라갑니다.** ALFA는 이 제품을 보안 테스트용으로 포지셔닝했습니다. 모니터 모드는 바로 사용할 수 있지만, 패킷 인젝션은 커널 버전에 따라 다릅니다(3.2절 참조).

## 3. Kali Linux에서의 AWUS036AXML: 실전 플러그 앤 플레이와 모니터 모드

### 3.1 꽂고, 확인하고, 작업 시작: 세 단계

어댑터를 USB-C 포트에 꽂은 다음(포함된 USB-C/USB-A 2-in-1 케이블이 도움이 됩니다) 실행합니다.

```bash
lsusb                 # ID 0e8d:7961인 MediaTek 디바이스가 표시되어야 함
ip link               # wlanX 인터페이스가 나타나야 함
sudo apt install linux-firmware firmware-misc-nonfree
sudo reboot
```

재부팅 후 인터페이스를 확인합니다.

```bash
iwconfig              # wlanX가 Managed 모드로 표시되어야 함
ip addr show wlanX    # 주소가 정상적으로 할당됨
```

기본 연결의 경우에도 주류 배포판(Kali 포함)의 NetworkManager가 직접 인식합니다 — **GitHub 소스 사이트가 필요 없습니다.**

처음 AXML을 Kali에 꽂았을 때, `lsusb`에서 `0e8d:7961`을 본 것만으로 안심이 되었습니다 — 클론도, 컴파일도 없이 재부팅 후 인터페이스가 스스로 나타났습니다.

### 3.2 모니터 모드 및 패킷 인젝션 테스트

인터페이스가 `wlan1`이라고 가정하면:

```bash
sudo ip link set wlan1 down
sudo iw dev wlan1 set type monitor
sudo ip link set wlan1 up
iw dev wlan1 info     # type이 monitor로 표시되는지 확인
```

이제 끝입니다 — `wlan1`은 802.11 프레임을 수동으로 청취하며, Wireshark나 aircrack-ng 묶음을 사용할 준비가 되었습니다.

다음으로 패킷 인젝션을 테스트합니다.

```bash
sudo aireplay-ng --test wlan1
```

kernel 6.16 이전의 커뮤니티 보고에서는 네이티브 `mt7921u` 드라이버에서 `Injection is working!`(또는 동등한 출력)이 보였습니다. 하지만 stock kernel 6.16 이상(ASUS GX10, Ubuntu 24.04 ARM64, kernel 6.17에서 실측)에서는 인젝션 테스트가 실패합니다. `aireplay-ng --test`가 Found 0 APs / No Answer를 표시하므로 deauth나 handshake 캡처를 할 수 없습니다. 원인은 kernel 6.16부터의 mac80211 chanctx 회귀이며 칩 자체의 한계가 아닙니다. 커뮤니티 patched 드라이버로는 인젝션이 작동하지만 펌웨어가 여전히 전송 속도를 고정합니다(1/6 Mbps, HT/VHT 인젝션 불가). 인젝션이 필요하면 AWUS036ACH, EACS 또는 ACS를 사용하십시오.

### 3.3 융합 모드(VIF): 관리와 모니터링을 동시에

많은 침투 시나리오에서는 어댑터가 "클라이언트로 온라인 상태를 유지하면서 동시에 모니터링"하기를 요구합니다. 네이티브 드라이버는 가상 인터페이스(Virtual Interface)를 통해 이를 지원합니다.

```bash
sudo iw dev wlan1 interface add mon0 type monitor
sudo ip link set mon0 up
```

이제 `wlan1`은 관리 모드(인터넷용)를 유지하고, `mon0`은 모니터링을 담당합니다. RTL8812AU 드라이버에서 이를 안정적으로 작동시키려면 보통 설정 파일 한 무더기를 편집해야 하지만 — 네이티브 드라이버는 이 기능을 그냥 손에 쥐여줍니다.

> **⚠️ 합법 사용의 금지선**: 모니터 모드, 패킷 인젝션, Evil Twin 같은 기능은 **본인이 소유하거나 명시적으로 테스트 허가를 받은 네트워크에서만**(본인 실험실, 회사 승인 테스트 구간) 테스트하십시오. 무단 네트워크 정찰이나 침입은 현지 법률을 위반할 수 있습니다. 법적 경계 안에 머무르십시오 — 이 글은 학술 및 공학 목적의 기술 설명입니다.

## 4. 구매 전 평가 워크시트: "네이티브, 무컴파일"인가, "DKMS 어댑터"인가?

구매 후 지원 비용을 낮추려면, AWUS036AXML과 AWUS036ACH 사이에서 결정하기 전에 이 빠른 평가를 해보십시오.

### 4.1 두 어댑터 나란히 비교

| 평가 항목 | AWUS036AXML (MT7921AUN) | AWUS036ACH (RTL8812AU) |
|---|---|---|
| 무선 사양 | Wi-Fi 6E 트라이밴드 (2.4/5/6 GHz) | AC1200 듀얼밴드 (2.4/5 GHz) |
| USB 인터페이스 | USB-C (USB 3.2 Gen 1) | USB 3.0 Type-A |
| Linux 드라이버 | `mt7921u` **커널 5.18+ 네이티브 내장** | 외부 DKMS 컴파일 필요 |
| 설치 난이도 | 펌웨어만 추가 | 툴체인 + 컴파일 + (Secure Boot 시) 서명 |
| 커널 업그레이드 영향 | 없음 | 업그레이드마다 재컴파일 |
| 모니터 모드 | 네이티브 지원 | 지원 |
| 패킷 인젝션 | ⚠️ kernel 6.16 이전 커뮤니티 보고 있음, 6.17 실측 실패 | 지원 |
| macOS | 지원 안 됨 | 지원 안 됨 |
| 적합 대상 | 현대 Linux / Kali / 임베디드 | 구형 시스템 또는 2.4/5 GHz 시나리오 |

### 4.2 30초 결정 체크리스트

체크하는 항목이 많을수록 **AWUS036AXML이 올바른 선택**입니다.

- [ ] 주 시스템이 커널 5.18 이상의 **Kali Linux / Ubuntu / Debian**이다.
- [ ] `dkms`도, `github clone`도, 빌드 툴체인도 없이 **기본 상태로 바로 작동**하기를 원한다.
- [ ] 네이티브 `mt76` 계열 지원을 원하며, 커널 업그레이드가 어댑터에 영향을 주면 안 된다.
- [ ] **6 GHz 대역**(Wi-Fi 6E 라우터 환경)이 필요하다.
- [ ] 주 용도: 모니터링, Soft AP, 융합 모드(VIF) (패킷 인젝션은 kernel 6.16 이상에서 작동하지 않음, 3.2절 참조).
- [ ] 포함된 USB-C / USB-A 2-in-1 케이블을 노트북이나 단일 보드 컴퓨터와 함께 사용할 것이다.

반대로, 6 GHz가 필요 없고 시스템이 5.18 미만의 구형 커널을 구동하며 DKMS 유지보수 워크플로에 익숙하다면, AWUS036ACH도 여전히 자리가 있습니다. 다만 마음의 준비는 하십시오. 커널 업데이트마다 드라이버를 재컴파일해야 한다는 것을.

---

## 5. 결론

현대 Linux와 Kali 개발자에게 시간은 가장 큰 비용입니다. **MediaTek MT7921AUN(AWUS036AXML)는 끝없는 드라이버 유지보수 부담을 당신의 어깨에서 덜어줍니다.** 드라이버는 커널 안에 있고, 펌웨어는 하나의 패키지로 오며, 모니터링이 기본 상태로 작동하며(패킷 인젝션은 stock kernel 6.16 이상 실측에서 실패하므로 필요하면 ACH, EACS 또는 ACS를 사용하십시오) — 롤링 커널 업데이트는 전혀 두려울 것이 없습니다.

구매 전에는 단 두 가지만 확인하면 됩니다. **커널 ≥ 5.18**, 그리고 **macOS가 아닐 것**. 나머지는 네이티브 드라이버가 처리합니다.

## 부록: 빠른 문제 해결 접수표 (지원 및 사용자용)

어댑터를 꽂은 후 인터페이스가 나타나지 않으면 순서대로 확인하십시오.

1. `lsusb`에 `0e8d:7961`(MediaTek)이 표시되나요? → 아니라면 다른 USB 포트를 시도하거나 전력 공급을 확인하십시오.
2. `sudo apt install linux-firmware firmware-misc-nonfree`를 실행하고 재부팅하십시오 → 펌웨어 누락이 1순위 원인입니다.
3. `ip link`에 `wlanX`가 표시되나요? → 아니라면 커널 버전(`uname -r`)이 5.18 이상인지 확인하십시오.
4. **먼저 OS가 macOS가 아닌지 확인하십시오** — 이 제품에는 macOS 드라이버가 없습니다; 이 문제로 수리를 보내지 마십시오.
5. 위가 모두 괜찮은데도 모니터링이 여전히 실패하면, 실수로 관리 모드에 있는 것은 아닌지 확인하십시오(`iw dev wlanX info`로 type 점검).

> 면책 조항: 여기서 설명한 드라이버 지원 및 커널 버전은 Linux 메인라인과 주요 배포판의 공식 패키지를 기준으로 합니다; 패키징과 커널 구성은 배포판마다 약간 다를 수 있습니다. 이 글은 어떤 상용 폐쇄 소스 플랫폼이나 브랜드에 대해서도 공식 호환성을 약속하지 않습니다. 모든 기능 테스트는 법적으로 허가된 환경에서 수행하십시오.
