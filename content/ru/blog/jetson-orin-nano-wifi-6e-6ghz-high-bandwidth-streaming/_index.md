## Введение: откуда берётся «потолок пропускной способности» у периферийных устройств?

Подключить Jetson Orin Nano к точке доступа (AP) и запустить две-три IP-камеры выглядит обычным делом. Но когда Вы действительно отправляете несколько **потоков 4K в реальном времени** в GPU для инференса, многие впервые ощущают предел беспроводной сети:

- Качество изображения постоянно падает (bitrate не растёт, картинка становится туманной или блочной).
- Задержка скачет, и «временное смещение» инференса моделей ИИ для видео становится всё заметнее.
- Планирование застревает, экран центра управления чернеет, а при проверке выясняется «потеря пакетов по беспроводной сети».

Эта статья разбирает проблему пропускной способности «многопоточного RTSP 4K-стриминга на периферии» с трёх сторон: **физический уровень → уровень настройки → уровень измерений**. Затем показано, как подключить **адаптер AWUS036AXML Wi-Fi 6E** к **Jetson Orin Nano (JetPack / Ubuntu 22.04 LTS)** и перейти в чистый **диапазон 6GHz**. В конце данные доказывают, «почему 6GHz — первый выбор для такого рода нагрузки».

Если Вы ещё не решили, покупать ли эту карту, рекомендуем сразу перейти к «Контрольному списку совместимости перед покупкой» в главе 4 и отметить каждый пункт.

## 1. Многопоточный RTSP 4K-стриминг на периферии: проблемы пропускной способности и помех в беспроводной сети

### 1.1 Сначала посчитаем: сколько пропускной способности нужно одному 4K-потоку?

RTSP (Real-Time Streaming Protocol) — это лишь протокол «рукопожатия и управления»; реальные видеоданные передаются в пакетах RTP. На примере выхода типичных коммерческих IP-камер:

| Выход камеры | Кодек | Реальный трафик на поток (зависит от настроек качества) |
|---|---|---|
| 1080p30 | H.264 | около 4 – 8 Mbps |
| 4K (2160p)30 | H.264 | около 20 – 35 Mbps |
| 4K (2160p)30 | H.265 | около 10 – 20 Mbps |
| 4K (2160p)30 (настройки высокого bitrate и низкой задержки) | H.264 | до 45 Mbps+ |

> **Ключевой момент**: 4K — это «монстр»: **каждый поток потребляет в 2,5–8 раз больше пропускной способности, чем HD**. Четыре потока 4K/H.264 одновременно на плату — это **80–140 Mbps «эффективной полезной нагрузки»**. Обратите внимание: **эффективная полезная нагрузка**, а не беспроводная скорость PHY — разница между ними почти двукратная (см. раздел 1.3).

### 1.2 Потеря пакетов ≠ проблема сигнала: беспроводная среда полудуплексная и общая

Многие считают, что «если сигнал полный, значит, проблем нет», но в периферийных средах настоящий убийца — **перегрузка**:

- **В 2.4GHz осталось только 3 неперекрывающихся канала**: Bluetooth, микроволновые печи и точки доступа соседних цехов — всё теснится здесь. Из-за механизма отката (backoff) в CSMA/CA пропускная способность падает вдвое, а затем ещё вдвое по мере роста числа устройств.
- **5GHz лучше, но это всё ещё поле боя**: плотность 5GHz в квартирах, офисах и на заводах доводит загрузку каналов до предела.
- **Беспроводная среда общая**: какой бы высокой ни была скорость PHY, если на канале есть кто-то ещё, Ваши пакеты ждут. Контроль перегрузки TCP в результате постоянно снижает скорость.

### 1.3 Почему «PHY 2400 Mbps» не равно «передаче 2400 Mbps»?

Беспроводная пропускная способность несёт много потерь — это физический факт:

1. **Протокольные накладные расходы (Overhead)**: заголовки кадров Wi-Fi, ACK, Beacon и окно конкуренции CSMA/CA съедают около 30–50% скорости PHY.
2. **Потери из-за окружения**: расстояние, стены и отражения от металла заставляют PHY автоматически понижать модуляцию (с высшего MCS до более низкого MCS).
3. **Двунаправленное планирование**: загрузка видео (uplink) и управляющая выгрузка (downlink) используют один и тот же беспроводной канал.

Поэтому карта класса 2400 Mbps **в чистой среде обычно даёт 600–900 Mbps реальной полезной нагрузки** — с запасом для многопоточного 4K (80–140 Mbps). Но **как только она попадает в перегруженный канал 2.4G/5G, реальные измерения часто падают до 100–300 Mbps** — мгновенное узкое место.

### 1.4 Три «базовых значения», которые стоит измерить заранее

Прежде чем менять какое-либо оборудование, зафиксируйте текущие цифры (эти данные также служат передачей Intake для послепродажной диагностики):

```bash
# 1) Ядро и система
uname -r
grep PRETTY /etc/os-release

# 2) Текущий беспроводной интерфейс и сигнал
iw dev                      # список беспроводных интерфейсов
iw dev wlan0 link           # текущие AP, канал, RSSI, bitrate

# 3) Загрузка канала на стороне AP (выполнить на AP или посмотреть в WebUI AP)
#    Базовый уровень проверки связи
ping -c 60 -i 1 <IP_ШЛЮЗА_AP>
```

Запишите RSSI, bitrate, задержку ping и процент потери пакетов «старой карты / старого диапазона» — в конце главы 3 Вы сравните их с 6GHz.

## 2. Настройка AWUS036AXML Wi-Fi 6E в JetPack (Ubuntu 22.04 LTS)

### 2.1 Сначала проверьте версию ядра JetPack

Главное преимущество AWUS036AXML в том, что **драйвер `mt7921u` чипсета MediaTek MT7921AU нативно интегрирован в основное ядро Linux** (включён с Kernel 5.18), **компилировать драйвер из GitHub не нужно**. Но у «нативной поддержки» есть порог; сначала проверьте версию ядра:

```bash
uname -r
```

Справочная таблица:

| JetPack | Базовая ОС | Linux Kernel | Поддержка AWUS036AXML |
|---|---|---|---|
| JetPack 5.1.x | Ubuntu 20.04 (проверить самостоятельно) | 5.10 | Драйвер нужно проверять; рекомендуем сразу обновиться до JetPack 6.x |
| JetPack 6.0 / 6.1 | Ubuntu 22.04 LTS | 5.15 | Зависит от версии ядра; сначала выполните `modinfo mt7921u` |
| JetPack 6.2+ (рекомендуется) | Ubuntu 22.04 LTS | 6.1 | `mt7921u` встроен нативно, работает сразу после подключения |

Проверьте готовность драйвера и прошивки:

```bash
modinfo mt7921u                         # есть вывод = драйвер уже встроен в ядро
sudo apt update
sudo apt install linux-firmware         # убедиться, что прошивка MediaTek актуальна
sudo reboot
```

> **Граница поддержки (Support Reduction)**: AWUS036AXML **не поддерживает macOS (ни Intel, ни Apple Silicon)**. JetPack работает только в собственной среде Ubuntu 22.04 LTS для Jetson, и все команды в этой статье предполагают Linux; если Ваш основной компьютер — Mac, используйте любой Linux-хост в качестве периферийного вычислительного узла.

### 2.2 Подключение адаптера к Jetson: порты USB и питание

Jetson Orin Nano Developer Kit предоставляет 2 порта USB 3.2 Type-A (синие) и 2 порта USB 2.0. AWUS036AXML использует интерфейс **USB-C 3.2 Gen1** и поставляется с комбинированным кабелем 2-в-1 (USB-C на USB-A) для питания и данных:

```bash
# После подключения убедитесь, что устройство распознано на уровне USB (VID:PID чипсета MediaTek MT7921AU — 0e8d:7961)
lsusb | grep -i mediatek
```

**Предупреждение о питании (частый убийца на практике)**:

- AWUS036AXML потребляет около **2.7W максимум**; прямое подключение к порту USB 3.2 Jetson обычно не проблема.
- Если Вы одновременно используете несколько мощных адаптеров, внешний SSD и USB-камеры, **рекомендуем USB-хаб с отдельным питанием (Powered Hub)**, чтобы избежать мгновенных просадок напряжения, из-за которых адаптер «то появляется, то исчезает».
- Не используйте удлинители и разветвители на передней панели: чем короче и толще USB-кабель, тем лучше.

### 2.3 Подключение к точке доступа и фиксация диапазона

JetPack управляет беспроводными сетями через NetworkManager:

```bash
# Сканирование и подключение
nmcli device wifi list
nmcli device wifi connect "ВАШ_SSID" password "ВАШ_ПАРОЛЬ"
```

**Фиксация диапазона (ключевой шаг)**: значение `nmcli band` — `bg` для 2.4GHz и `a` для 5GHz; **6GHz в Wi-Fi 6E использует `a` (расширенный)**. Самый надёжный способ — создать на **стороне точки доступа** выделенный SSID «**только 6GHz**» и отключить Band Steering, а затем подтвердить, к какому диапазону реально подключился клиент, по содержимому физического канала:

```bash
# Проверка текущего канала подключения (частоты 6GHz лежат в диапазоне 5925–7125 MHz)
iw dev wlan0 link

# Чистый способ проверки: посмотреть, в какой диапазон попадает частота
iw dev wlan0 link | grep -i freq
#   2.4GHz → 2400-2500 MHz
#   5GHz   → 4900-5900 MHz
#   6GHz   → 5925-7125 MHz (только Wi-Fi 6E)
```

Если Вы не хотите, чтобы клиент роумингом уходил в перегруженные 2.4/5GHz, зафиксируйте это в настройках подключения:

```bash
nmcli c show --active                       # найти имя подключения
nmcli con mod "ИМЯ_ПОДКЛЮЧЕНИЯ" 802-11-wireless.band a
nmcli con up "ИМЯ_ПОДКЛЮЧЕНИЯ"
```

> **Регуляторное предупреждение**: доступность диапазона 6GHz зависит от нормативов Вашей страны/региона и **прошивки точки доступа**. Например, на Тайване NCC открыла для 6GHz диапазон **5945–6425 MHz**, **только для использования внутри помещений с малой мощностью**, а не полный 5925–7125 MHz. Если `iw reg get` показывает регуляторный домен (regulatory domain) без 6GHz, или на AP не включён 6GHz, адаптер просто не подключится — это не аппаратная неисправность, а проблема нормативов/настройки.

## 3. 6GHz против перегруженных 2.4G/5G: измерение пропускной способности и задержки

> Дух измерений: **тот же Jetson, тот же адаптер, та же точка доступа, та же дистанция** — меняется только диапазон, остальные условия неизменны. Только так измеренная разница будет разницей самого «диапазона».

### 3.1 Спроектируйте контрольный эксперимент

| Переменная | Способ контроля |
|---|---|
| Расположение AP | Фиксировано; все три диапазона используют одну точку доступа Wi-Fi 6E |
| Дистанция | Фиксирована (например, 3 метра по прямой без препятствий) |
| Время | Тот же день, близкие часы (перегрузку 2.4/5GHz измеряем на месте) |
| Адаптер | Тот же AWUS036AXML, меняется только SSID |
| Среда помех | Сохраняем существующие помехи (в этом и смысл «реальных измерений») |

### 3.2 Измерение 1: RSSI и пропускная способность одиночного канала (iperf3)

Установите iperf3 на Jetson и подключите его к принимающему хосту:

```bash
# Принимающая сторона (например, другой компьютер или сервер)
iperf3 -s

# Сторона Jetson (клиент, 60-секундный двунаправленный прогон)
iperf3 -c <IP_ПРИЁМНИКА> -t 60 -R     # -R измеряет reverse (загрузка с Jetson)
```

Запустите по одному разу на **SSID 2.4GHz, SSID 5GHz и SSID 6GHz**, записывая `sender Mbps` и `receiver Mbps`. Можно также сначала посмотреть качество соединения:

```bash
iw dev wlan0 link                              # RSSI + текущий PHY bitrate
iw dev wlan0 station dump | grep -E "signal|tx bitrate|rx bitrate"
```

### 3.3 Измерение 2: связь и задержка (ping)

```bash
ping -c 60 -i 1 <IP_ПРИЁМНИКА> | tail -2
```

Запишите для трёх групп: **среднюю задержку (ms)**, **процент потери пакетов (%)** и **джиттер задержки (max-min)**.

### 3.4 Измерение 3: реальный многопоточный RTSP 4K-стриминг (стресс-тест GStreamer)

Пропускная способность и задержка — лишь косвенные показатели; **по-настоящему нужно проверить, «сколько потоков 4K декодируется одновременно без потери кадров»**. В JetPack встроен плагин аппаратного декодирования NVIDIA для GStreamer 1.0 (`nvv4l2decoder`):

```bash
# Используйте элемент perf для подсчёта реальной частоты декодирования (выборка раз в 1 секунду)
gst-launch-1.0 \
  rtspsrc location="rtsp://IP_КАМЕРЫ/stream" ! \
  rtph264depay ! h264parse ! nvv4l2decoder ! nvvidconv ! \
  perf print-stats=true ! fakesink
```

Откройте несколько терминалов, по одному потоку 4K в каждом, и наблюдайте за GPU/памятью через `nvidia-smi` (на Jetson — `tegrastats`):

```bash
sudo tegrastats
```

**Критерии оценки**:
- Если `perf` каждого потока показывает **частоту dropped/rendered (FPS), стабильно приближающуюся к исходной (30fps)** → пройдено.
- Если на 2.4/5GHz кадры теряются или качество падает, а после переключения на 6GHz стабильность восстанавливается → это измеренное доказательство «перегрузки диапазона».

### 3.5 Пример ожидаемых результатов измерений

| Диапазон | PHY bitrate | iperf3: реальные upload/download | ping: среднее/джиттер | Результат многопоточного 4K-стриминга |
|---|---|---|---|---|
| 2.4GHz (перегруженный офис) | 300 Mbps | 80–120 Mbps | 8 ms / высокий джиттер, редкие потери | Падение качества, туманная картинка |
| 5GHz (умеренная загрузка) | 800 Mbps | 400–550 Mbps | 3 ms / средний | Работает с трудом, редкие подтормаживания |
| 6GHz (чистый выделенный SSID) | 1200 Mbps | 700–900 Mbps | 1–2 ms / стабильный | 2–4 потока 4K, всё зелёное |

> Это типичное сравнение «чистого и перегруженного». **Ценность 6GHz в том, что это новый диапазон, которым почти никто не пользуется**. В средах с плотным размещением камер и переполнением Wi-Fi-устройствами это преимущество сразу превращается в стабильную ёмкость для многопоточного 4K.

### Пакет информации Intake для службы поддержки
