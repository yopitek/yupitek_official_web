## 开场：开源圈口中的「数字图传天花板」到底是什么

商用数字图传系统（如 DJI 的 O3 / O4 系列）以「开机即用、交握（Handshake）快速、畫面稳定」聞名，但代价是**封闭协定、只能跟自家接收端配对、无法自行除错**。开源社群为了追求**自己能掌握、延迟够低、還能打长距离**的数字影像鏈路，走出了另一条路——**不要 WiFi 的「连接」，只要 WiFi 硬件去「广播」**。

今天的文章会依序拆解三件事：

1. 为什么开源高畫质图传需要把网卡切进**监听模式（Monitor Mode）**去广播 **Raw（原始）802.11 数据包**；
2. 三大主流开源图传**OpenHD vs. RubyFPV vs. WFB-ng** 的架构、延迟表现與多天线 **MIMO** 優勢对比；
3. 最常被忽略的**供电防坑**：为什么高功率 USB 网卡会让图传瞬间黑屏、甚至害飛控重新启动，以及**独立 BEC 外部供电**的正确接法。

主角是 ALFA **AWUS036ACH**（Realtek RTL8812AU）——开源数字图传社群里最常见的 USB 网卡之一。

## 一、为什么开源高畫质图传需要「监听模式广播 Raw 数据包」？

### 1.1 傳统 Wi-Fi 的「先握手、再傳输」包袱

你桌上的笔电连 WiFi 时，其实是一连串「社交礼仪」：

1. 网卡先扫描通道、找到 AP；
2. 跟 AP 进行 802.11 **连接交握（Association / Authentication）**，协商加密方式與金钥；
3. 通过 **DHCP** 取得 IP 位址；
4. 之后每个資料数据包都要经由 AP 转送，並仰赖 **ACK 确認、重传机制（Retransmit）與退避演算（Backoff）** 维持可靠度。

这套流程对「上网」非常棒，但对**飛行中的影像回傳**有三个致命問题：

- **延迟不稳（Jitter）**：交握、ACK、退避都是「有空才做」的作業，延迟可能从 5ms 突然跳到 100ms 以上；
- **斷线重连是灾难**：飛行器只要离开连接范围一瞬间，网卡就进入「重连地狱」，图传可能中斷数秒；
- **必須有一位「AP」**：固定主从架构，任何一端消失整条鏈路就報销。

飛行员要的不是「順暢上网」，而是**一个「极低且稳定延迟、单向、不怕斷頭」的傳输管道**。

### 1.2 开源图传的做法：不要连接，只要「广播」

开源数字图传把 WiFi 网卡切进 **监听模式（Monitor Mode，RFMON）**，再用软件直接用网卡**注入（Inject）未经连接交握的 Raw 802.11 資料数据包**，絲毫不进入 association / DHCP / ACK 流程——就只是「把数据包丟上空中」。

这項技术的正式名称是 **WiFi Broadcast（wifibroadcast）**，最早源自 2.4GHz 模拟时代的 OpenLRSng 等开源长距离遙控鏈路，后来在数字图传世代被 WFB-ng、OpenHD、RubyFPV 全面继承。

切进 Monitor Mode 的意義是**「擺脫操作系统與协定棧的束缚」**：网卡不再当「資料終端」，而是当「原始射频收发器」，由你的图传软件直接决定要送什么、怎么编码、要不要重传。

### 1.3 广播（Broadcast）带来的三項根本優勢

| 優勢 | 说明 |
|---|---|
| **One-to-Many（一对多）** | 飛行器一次广播，**不限数量的地面站都能同时收到**——多名飛手 / 观看者各带一台接收端即可，不必像影音串流得架服务器 |
| **延迟极低且可預期** | 少了逐数据包 ACK 與退避，鏈路的延迟主要来自**编码與 FEC 計算**，不再被 WiFi 的交握「抽樂透」 |
| **重建快速** | 飛行器不需要「重连」，只要每幀都重複广播資料，地面站随时加入就能随时接上畫面 |

另外，开源图传普遍加入 **FEC（向前错误更正，如 Reed-Solomon）**：把影像資料切成区塊、加上冗余码后一起广播。即使空中掉了一點数据包，地面站能在不解码失败的情況下直接补回——这是「单向广播」能维持畫质的关键。

### 1.4 为什么 RTL8812AU（AWUS036ACH）成了社群主流

要用 WiFi 广播技术当图传鏈路，网卡本身得够「听话」，Realtek **RTL8812AU** 的受歡迎来自三件事：

- **Monitor Mode + 数据包注入支持极佳**：这是歷经渗透测试社群千錘百煉的能力，开源图传同樣需要；
- **2×2 MIMO + 高发射功率**：双天线同时收发，让空间分集與吞吐量都有余裕，且在 5.8GHz 频段能拉到**兼具距离與畫质**的组合；
- **USB 3.0 接口**：資料面不会成为瓶頸，5GHz 连接的傳输速率可完整发揮。

ALFA **AWUS036ACH** 正是搭载 RTL8812AU、配備双 RP-SMA 5dBi 可拆天线的代表性型号——但「高功率」这三个字，同时也是第三節供电問题的根源，请继续往下讀。

## 二、OpenHD vs. RubyFPV vs. WFB-ng：三大开源图传协定对比

### 2.1 WFB-ng：只管「把数据包送出去」的底层鏈路引擎

**WFB-ng（Wideband FPV Next Generation）** 是 OpenLRSng 之后独立发展的开源项目，定位是**「无线資料鏈路框架」而非完整图传系统**——它负責把 **乙太网/串列数据包**通过网卡以 Wi-Fi 广播方式送出去，不含地面站 UI、不含影像编码。

- **底层架构**：Linux 原生工具鏈（`wfb_tx` / `wfb_rx`），將資料打进 Raw 802.11n 广播数据包，完全不进行 association；
- **MIMO**：完整支持 2×2，可使用 **MCS0–MCS15**（40MHz 下可达双流高傳输速率），这是它相較於旧方案吞吐上的最大武器；
- **延迟量级**：鏈路本身延迟极低（数毫秒等级），因为它只是一组「搬運工」；
- **适合誰**：**喜歡自己组装整套系统**的进階玩家、以及需要稳定低延迟點对點資料鏈路的机器人 / 无人車开发者（它也被大量用於非 FPV 的遙测與遙控任务）。

> 一句话：**WFB-ng 是「引擎」，不是「整台車」**。用它可以拉出媲美图传的黑科技鏈路，但视频编码、OSD、地面站 UI 都要自己蓋。

### 2.2 OpenHD：把 WFB-ng 包成「整台車」的完整生态

**OpenHD** 是目前开源数字图传社群最完整的「一站式」方案，在**飛行器端（Air）與地面站（Ground）**各提供整合的映像档（Image）與开机设定。

- **底层架构**：傳输内核承襲自 **Wifibroadcast → WFB-ng** 一脈的开放广播技术，上面再疊齐**影像编码、遙测（MAVLink / MSP）、RC 控制、OSD**等现代图传该有的功能；
- **视频**：支持 H.264 / H.265 硬件编码，並相容高幀率追蹤攝影机（如 Pursuit Camera 的 120fps 需求），畫面品质可視訊源與频道带宽调整；
- **多数据流**：**视频 + 遙测 + 遙控指令可以同一条鏈路同时跑**，不需额外数傳模组；
- **MIMO**：在 RTL8812AU 这类 2×2 网卡上充分利用双天线增益，延迟表现普遍落在 **30–70ms 量级**（端到端，实際依飛行器攝影机编码延迟、频道设定與干扰环境而异）；
- **生态**：社群活躍、文件齐全，地面站软件（QOpenHD）跨平台，並支持 HDMI 模拟眼鏡输入，相容性最高。

> 一句话：**OpenHD 是「买回家就能飛」的路线**，适合想快速把整套开源数字图传跑起来的人。

### 2.3 RubyFPV（Ruby）：开发者主导、轻量务实的另一条路

**RubyFPV（又称 Ruby）** 是社群开发者主导的另一个开源数字图传系统，走「**够用就好**」的路线：

- **底层架构**：同樣基於 5.8GHz WiFi 的广播 / 监听模式鏈路，飛行器端跑在 Raspberry Pi 等级的单板电脑上，视频由 CSI 攝影机或外接硬件编码器提供；
- **延迟量级**：與 OpenHD 同级（数十毫秒量级），着重「稳定」胜於「极限低延迟」，並內建 FEC 抗丢包；
- **MIMO**：於 RTL8812AU 上同樣能利用双天线的空间分集增益，改善障礙物下的信号稳定度；
- **地面站**：提供跨平台的接收软件，也支持以手机 / 平板当地面站显示，适合轻装出门的玩法；
- **定位**：系统相对精簡、硬件要求务实，适合**想要更少设定选項、更接近「即插即用」**的用户。

> 一句话：**RubyFPV 是「轻、快、少囉嗦」的路线**，硬件要求更务实。（註：各家项目演进速度快，实際功能以各官方儲存庫與文件为准。）

### 2.4 一张表看懂三个方案该怎么选

| 比較項目 | OpenHD | RubyFPV | WFB-ng |
|---|---|---|---|
| 定位 | 完整图传生态（Air + Ground） | 轻量图传系统 | 底层无线鏈路框架 |
| 底层鏈路 | Wifibroadcast / WFB-ng 体系 | 5.8GHz WiFi 广播鏈路 | 原生的 Raw 802.11n 广播框架 |
| 延迟量级（端到端） | 约 30–70ms（依硬件與设定） | 数十 ms 级 | 鏈路本身僅数 ms，其余自理 |
| 2×2 MIMO | ✓（充分利用） | ✓（空间分集） | ✓（MCS0–MCS15 完整支持） |
| 视频编码 | H.264 / H.265，支持高幀率追蹤攝影机 | H.264 / H.265（依编码器） | 不含（需自行搭配） |
| 多数据流 | 视频 + 遙测 + RC 並行 | 视频 + 遙测 | 通用資料鏈路（可承载多種資料） |
| 上手难度 | 中（直接刷映像档） | 中低 | 高（需自行组装整条鏈路） |
| 适合誰 | 想整套快速起飛 | 轻装、务实派 | 进階开发者 / 机器人项目 |

### 2.5 我們该用哪一个？

- **第一次玩开源数字图传 →** 选 **OpenHD**，映像档刷了就能测，社群資源最多；
- **想要轻量化、硬件越少越好 →** 试 **RubyFPV**；
- **你不是在飛无人机，而是在做机器人 / 遙控車的資料鏈路，或想徹底掌控每一层 →** 用 **WFB-ng** 自己蓋。

不管选哪个，**它們的共同底层硬件幾乎都是「一张能进 Monitor Mode 的 5GHz USB 网卡」**——也就是 AWUS036ACH 这类 RTL8812AU 掌管的領域。而最常让新手翻車的不是软件，是**电力**。

## 三、实战避坑：高功率网卡的电流尖峰與外部 BEC 供电

### 3.1 常见症状：图传「正常起飛 30 秒后开始閃黑屏，然后飛控重启」

开源图传社群最经典的求助文长这樣：

> 「我的 Pi + AWUS036ACH 在地上测都正常，一升空、一加速就斷图传；看日誌看到 **USB disconnect**，前后脚飛控就重启了，我是不是买到卡王？」

**这不是网卡故障，是供电。** 而「一升空才发生」是因为——推力大、馬达电流大、电池电压开始被拉低，系统的**余裕（Headroom）**刚好在那一瞬间见底。

### 3.2 物理原因：射频功率放大器（PA）的「瞬间瞬态抽载」

AWUS036ACH 內建**高功率放大器（Power Amplifier，PA）**，这正是它能打远的原因，但也正是耗电元兇：

- **规格标示**：AWUS036ACH 最大耗电约 **0.7A @ 5V**；
- **但规格是「平均上限」**：PA 在**每个数据包发射的瞬间**、特别是**高 MCS + 40MHz 带宽 + 滿功率**时，瞬时瞬态抽载的电流尖峰**会明显超過平均值的数百毫安甚至上千毫安**；
- 当 USB 5V 供应跟不上这波尖峰：**电压瞬间跌落（Voltage Sag）→ 网卡掉电重新列舉（dmesg 出现 `usb 1-1: device descriptor read error` / `USB disconnect`）→ 图传中斷**。

如果这张网卡**跟飛控共用同一条 5V 电源軌（BEC）**，或**直接吃机载电脑（Raspberry Pi）的 USB 接口**，后果更嚴重：瞬间瞬态抽载让整条 5V 軌道压降（Brown-out），**飛控 MCU 與伺服供电一同跌破工作电压 → 飛控直接重新启动**。这不是玄學，是电源设計問题。

### 3.3 为什么「高功率网卡」特别要独立供电

Raspberry Pi 官方建议 **Pi 3B+ / 4 需要 2.5A–3A（5V）电源供应器**，Pi 5 甚至建议 5V/5A——这已经是「只養 Pi 自己」的預算。当你在 Pi 的 USB 接口上再挂一张高功率 AC 网卡：

- Pi 的 USB 接口能提供的稳定电流有限，且**要跟 Pi 本身搶 5V 电源**；
- 飛行器上若整机只用**一顆小 BEC 同时餵飛控 + Pi + 网卡**，功率預算幾乎必然爆表；
- 結论：**高功率网卡应「别吃 SBC 的 USB、别吃飛控的 BEC」，由独立电源專責供电**。

### 3.4 正确接法：独立 BEC / UBEC 外部供电

在飛行器端，把「电源」與「資料」分开，是整套系统稳定的关键。建议拓扑如下：

```
主电池 (LiPo 3S/4S/6S)
    │
    ├──▶ 飛控 ──▶ 电变/馬达
    │
    └──▶ 独立 5V BEC / UBEC（≥3A，預留电流余裕）
                │
                ├──▶ 5V → AWUS036ACH 网卡（电源接頭，例如随附的 USB 线改由 BEC 供电）
                │
                └──▶ 5V → 机载电脑（Pi）主电源输入（5V/GPIO 电源脚）

資料面（不承载电力）：
  Pi（机载电脑） USB3 ── USB 线 ──▶ AWUS036ACH   （只走資料）
  Pi（机载电脑） UART ── 遙测线 ──▶ 飛控 (MAVLink / TX/RX)
```

重點守则：

1. **独立 BEC**：选用额定 **≥3A**（出厂建议留有 30% 以上余裕）的 5V BEC / UBEC，从**主电池**取电，專責餵网卡（进階可與 Pi 分开各自一顆）；
2. **共地（Common Ground）**：BEC 的负极、飛控负极、网卡负极**必須接在一起**，避免地电位差造成信号错乱；
3. **电源與資料分离**：网卡供电走 BEC 專线，**不要**用同一条 USB 线既供电又傳資料给高功率网卡——USB 线的 5V 就是来自 Pi；
4. **靠近网卡加濾波**：在网卡电源输入端並聯 **470µF 低 ESR 电解电容**（吸收 PA 瞬间瞬态抽载）+ **磁珠 / LC 濾波**，把射频瞬间雜訊擋在网卡外；
5. **地面端同樣适用**：地面站若用笔电 USB 直供，务必用**供电充足、有强固电源输入的 USB 集线器（Powered Hub）**，别把地面网卡插在笔电只有 500mA 的旧接口上。

### 3.5 错误接法（请直接避开）

| ❌ 错误做法 | 后果 |
|---|---|
| 网卡直接插 Pi 的 USB 接口，還要飛控一起供电 | USB 接口的 5V 與 Pi 共用，PA 一瞬态抽载，Pi 压降 → **网卡重列舉 + 飛控重启** |
| 网卡电源吃「飛控的 5V BEC」 | 飛控供电軌道被拖垮，**遙控/姿态失效的瞬间最可怕** |
| 全部设備共用一顆 5A 以下的小 BEC | 功率預算爆表，各装置互相搶电，**莫名其妙重启的溫床** |
| 用「一条 USB 线同时供电與傳資料」接高功率网卡 | USB 线的 5V 来自 SBC，等於没分离电源 |

### 3.6 验證：用日誌與仪表留下證据

改完供电后，请实際验證（不验證 = 等於没修）：

```bash
# 1) 确認网卡接口與驅动状态
lsusb                          # 应看到 0bda:8812 Realtek 装置
iwconfig                       # wlanX 应显示为 Monitor 模式（图传设定下）

# 2) 观察 USB 大量傳输期间是否出现斷线日誌
dmesg -w | grep -iE "usb|disconnect|over-current"

# 3) 停用 RTL8812AU 的 USB 省电（官方建议，降低掉线机率）
sudo tee /etc/modprobe.d/8812au.conf <<'EOF'
options 8812au rtw_power_mgnt=0 rtw_enusbss=0
EOF
sudo reboot
```

> 量测建议：用**功耗計（USB Power Meter）**或电錶在网卡电源输入端量测**峰值电流**；升空（馬达高负载）时系统若稳定启动且 `dmesg` 无 `disconnect`，供电才算過关。若网卡供电只能由 SBC 提供（地面站使用情境），请改用**外部供电的 Powered USB Hub**，道理完全相同。
